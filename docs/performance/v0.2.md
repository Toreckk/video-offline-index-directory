# v0.2.0 Performance Evidence and Decisions

## Test profile

- Date: 2026-08-22
- Host: Windows x86-64, AMD64 Family 25 Model 97, Node.js 24.11.1
- Fixtures: 2,500 and 5,000 synthetic MP4 assets, 300 tags, five assignments per annotated video
- Commands:
  - `pnpm bench:v0.2`
  - `cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml five_thousand -- --nocapture`
- The JavaScript render benchmark uses React development builds in jsdom. It is deliberately conservative and is a regression comparison, not a claim about production frame timing.

## Results

| Workload | 2,500 videos | 5,000 videos |
| --- | ---: | ---: |
| 1% catalog reconciliation, mean | 2.13 ms | 4.55 ms |
| Tag usage counts, mean | 0.32 ms | 0.70 ms |
| Filter + filename sort, mean | 0.62 ms | 1.28 ms |
| Virtualized Explorer mount, one conservative sample | 180 ms | 137 ms |

Native desktop measurements:

| Workload | Result |
| --- | ---: |
| Discover 5,000 files | 570 ms |
| Serialize + transactionally save 5,000-asset SQLite catalog | 99 ms |
| Load + deserialize 5,000-asset SQLite catalog | 44 ms |

The exploratory pre-virtualization render mounted every rich media tile and took about 4.2 seconds at 2,500 assets and 11.1 seconds at 5,000. The committed virtualized harness mounts only visible and overscanned rows, keeps the full player queue, and reduces the 5,000-video mount by more than 98%. Live Tauri QA with a 2,436-video library confirmed correct scrolling and responsive column changes in restored and maximized windows.

## Virtualization decision: implement in v0.2.0

The data transformations are already comfortably below a 16 ms frame budget at 5,000 assets; the expensive work was constructing thousands of interactive React tiles and their controls. V.O.I.D. now virtualizes the responsive grid with TanStack Virtual, retains the existing design, and exposes the total list size and position to assistive technology. The dependency is a headless measurement utility, so markup and styling remain owned by V.O.I.D. See the [TanStack Virtual introduction](https://tanstack.com/virtual/latest/docs/introduction) and [Virtualizer API](https://tanstack.com/virtual/latest/docs/api/virtualizer).

## FFmpeg decision: do not bundle in v0.2.0

`ffprobe` would provide reliable, machine-readable stream metadata and FFmpeg could generate thumbnails independently of WebView codec support. The official [ffprobe documentation](https://ffmpeg.org/ffprobe.html) confirms that role. It remains a good candidate for a separately measured native-media adapter.

It is not justified for this release:

- Current v0.2 bottlenecks were catalog churn and React tile mounting, both addressed without a media sidecar.
- A representative current Windows x86-64 LGPL package is roughly 64.6 MiB compressed for shared binaries or 141.6 MiB for a static package, before installer impact. See the [BtbN Windows build table](https://github.com/BtbN/FFmpeg-Builds/releases).
- FFmpeg is LGPL 2.1-or-later by default, while optional GPL parts change the applicable terms. Distribution needs a deliberate binary provenance, notices, source-offer, and update process; see [FFmpeg's legal guidance](https://ffmpeg.org/legal.html).
- Adding a large native binary late in v0.2 would expand codec, packaging, security-update, and installer QA scope.

Next step: prototype an LGPL-only `ffprobe`/thumbnail sidecar behind the existing media port on a separate branch, measure success rate and throughput against the WebView implementation, and reconsider it for v0.3.0. V.O.I.D. v0.2.0 continues to use the existing two-pass WebView thumbnail path and records unsupported/corrupt media in Library Health.
